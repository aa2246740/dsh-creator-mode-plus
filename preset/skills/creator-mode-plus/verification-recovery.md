# Verification and recovery

## Choose a verification path

Use the actual product entry: the plugin's slash command, tool or service for
server behavior; the authenticated page for UI behavior. Reuse an authenticated
app/page through this task's permitted computer/browser tools. Creator+ does not
require its adapter when that authorized UI is already available.

If a new browser context needs authentication, read
`dshx kb cat contracts/browser-access`, then call `dshx_browser_open({})`.
The bridge supplies private official Connection input. After
`BROWSER_AUTHENTICATED`, continue testing the feature in this task.

| Result | Scope and response |
|---|---|
| `BROWSER_ADAPTER_REQUIRED` or adapter failure | Browser automation is unavailable. Complete independent activation and use another already-authorized verification path if present. Report the remaining UI step once. |
| `WEB_AUTH_REQUIRED`, expired binding, changed Host | Current-Host proof is unavailable. Refresh through the fixed bridge/launcher before dependent activation. Preserve source and claims. |
| Missing manifest or failed bundle response | Identify which package and runtime layer failed before diagnosing feature behavior. |

Adapter setup requires an externally reviewed, session-bound executable. Complete
independent work while it is pending. It grants neither a new browser provider
nor a different workspace. A browser-only blocker does not require upgrading
Harness, modifying the App or restarting the Host. Keep credentials inside the
configured private bridge handoff, outside conversation, logs and model arguments.

## Activation failure

Preserve the exact tool, target, error and rollback point. Stop the failed
operation and repair its prerequisite. Retrying unchanged bytes after the same
failure supplies no new evidence.

For a Guardian incident, read `dshx kb cat contracts/creator-guardian`. Inspect
confidence, attribution, quarantine and log evidence. Repair source, build/check,
then retry the original activation branch. Guardian recovery is not functional
acceptance. Whole-plugin teardown remains the fixed remover's responsibility.

If a fixed tool throws `refusing an operation outside bridge v2`, report the
bridge integrity defect and preserve source. Repair/upgrade the bridge from the
external supervisor, then retry that fixed tool. Manual profile mutation, moving
the project or changing shells cannot repair its allowlist.

A failed hot reload clears its previous module receipt. Retry after changed
source or a resolved prerequisite. A launcher restart requires separate concrete
boot-boundary/recovery evidence and the corresponding authorization.

## Resume

After an authorized normal launcher restart, return to this conversation and call
`dshx_status`. Continue its recorded delivery and verify the current Host;
historical module proof belongs to its recorded PID. Keep the single real
`DSH_HOME` and original launcher. Cold-boot tests use a temporary Home and remove
the transient Host afterward. Preserve an explicit live user acceptance result
instead of restarting speculative diagnosis.
